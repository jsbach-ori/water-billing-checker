## 4. 公開方法の比較（どれもまだ実行していません）

### 方法A：今の履歴をそのままpushする
- **残る情報**
  - 全15件のコミットと、その中のすべての版
  - 過去のコミットの CLAUDE.md・PLAN.md に、絶対パス（Windowsのユーザーフォルダ名）と別のプロジェクトの名前が残ります。GitHubで過去のコミットを開けば、誰でも見られます。
- **手間**：いちばん少ないです（`git remote add` と `git push -u origin main`）。
- **手元の開発履歴**：そのまま残ります。公開側でも、マイルストーンごとの開発の流れが見えます。
- **注意**：一度公開すると、あとで履歴を書き換えても、すでに見られたもの、複製されたもの、キャッシュされたものは消せません。

### 方法B：今のファイルだけを新しい履歴として公開する
- **残る情報**
  - 今のファイルだけです（1件のコミット）。絶対パスと別のプロジェクトの名前は、どこにも残りません。
  - 開発の経過は、`docs/reports/` と PLAN.md のチェックで読めます。ただし、コミットごとの差分は見られません。
- **手間**：少ないです。
  1. 今の main を手元の別名ブランチ（例：`dev-history`）として残す
  2. 履歴を持たないブランチを作って、今のファイルを1件のコミットにし、それを新しい main にする
  3. `main` だけをpushする（`--all` や `--mirror` は使わない）
  - 公開前の確認：新しい main の全履歴を、今回と同じ方法で検索します。
- **手元の開発履歴**
  - `dev-history` ブランチとして手元に残ります。pushはしません。
  - 必要なら、`git bundle` で1つのファイルに保存しておけます。
  - 以後の開発は、新しい main に積み上げます。古い履歴と新しい履歴はつながらないので、差分を比べるときは手元で `dev-history` と比べます。

### 方法C：過去のコミットの2つのファイルだけを書き換える（参考）
- **残る情報**
  - 15件のコミットと開発の流れは残ります。
  - 全コミットの CLAUDE.md・PLAN.md の該当行が、今回の直した文になります。
- **手間**：中くらいです。
  - Git に入っている `git filter-branch` で書き換えます。この方法は推奨されなくなっていますが、使うことはできます。`git filter-repo` は入っていませんし、ツールは追加しません。
  - すべてのコミットのIDが変わります。報告書の中にはコミットIDを書いていないので、文書の直しは要りません。
  - 書き換えたあと、全履歴を再び検索して確かめる必要があります。
- **手元の開発履歴**：書き換える前の履歴を、バックアップのブランチに残せます。

### 推奨
**方法B** をおすすめします。
- 理由
  - 消したい情報が履歴に残らないことを、新しい main の1件のコミットを検索するだけで確実に確かめられます。
  - 手間とリスクがいちばん少ないです。
  - 開発の経過は `docs/reports/` と PLAN.md で伝わります。
  - 元の履歴は、手元の `dev-history` ブランチとして失わずに残せます。
- 方法Cが向いている場合：コンテストで、コミットの積み重ね（開発の過程）そのものを見せたい場合です。
- 方法Aは、ユーザーフォルダ名と別のプロジェクトの名前が公開されてもよい場合だけになります。

**決めていただきたいこと**：A・B・C のどれで公開するか
